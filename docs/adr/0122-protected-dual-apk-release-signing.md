# ADR 0122: protected, fail-closed dual-APK signing

- Status: Accepted for release engineering; production-key execution pending owner configuration
- Scope: M0 release pipeline; does not promote protocol maturity

## Problem and decision

The release workflow assumed `receiver-release.apk`, but both Gradle applications
have no signingConfig and produce `*-release-unsigned.apk`. It also omitted
Sender. Thus green normal CI did not prove an actual tag release could collect
installable APKs. The owner selected GitHub protected Environment secrets for
long-term automatic signing; no production key is generated by this increment.

Build both production variants without secrets, validate their identity/version,
native ABI and absence of test-only code, then hand off exact hashes/commit via
an immutable artifact ID. A separate `android-release` environment job, after
owner approval, uses four secrets and an independently pinned public certificate
SHA-256 to sign both APKs. The key file lives only in a fresh private temporary
directory, passwords are environment inputs to apksigner, diagnostics are static,
and child processes receive only an allowlisted environment. Zip alignment comes
before signing and is checked afterward; signatures and both fingerprints must
pass before publishing a complete output directory. Partial output and automatic
debug/unsigned fallback are forbidden. Cleanup removes temporary files, not a
promise of cryptographic erasure on hosted runner storage.

The unsigned build has read-only repository/check permissions and no production
environment. Only the environment-protected signing/publication job has release
write and OIDC attestation permission. No Gradle/build scripts run with signing
secrets. Production inputs are not provided to ordinary PR workflows. CI instead
exercises the same signer against both real APKs with a fresh two-day fixture key,
including negative fingerprint/password/missing-secret and cleanup paths.

Tag must be annotated/signed, strict SemVer, equal to the checkout and workflow
tag ref, and reachable from protected main. Its main CI/security gates must be
green. App versionName is the tag without v; versionCode is the complete main
first-parent count. Published versions use later main commits; tags cannot be
repurposed. Stable publication additionally requires explicit environment opt-in
after the actual PLAN gates; none is configured while product evidence is Partial.

## Environment state and migration

`android-release` was created with reviewer kairowan, `can_admins_bypass=false`,
and a `v*` tag-only deployment policy. Self-approval remains allowed for the sole
maintainer; do not confuse environment approval with independent PR approval.
At setup, it contained zero secrets. Values must be entered directly by the owner,
not pasted into the chat. See [operator guide](../ANDROID_RELEASE_SIGNING.md).

Previous developer APKs are debug-signed. Production signing changes their update
identity and cannot silently migrate stored data. A backup/migration decision is
still necessary; no automatic uninstall, key rotation, Play signing or production
publish was performed here. No new package dependency or protocol wire format.

## Verification and rollback

Python policy tests and actual platform signing smoke are required by CI. The
Windows smoke exposed a brief file-lock race on atomic directory rename; bounded
permission-error retries preserve atomic publication and fail closed afterward.
Linux CI exercises the full signing path independently. Main Rust/Android/security
gates remain required. Python security-extended CodeQL analysis of release and
repository tooling is a required dependency of `security-gate`, alongside
Actions, Rust and Kotlin analysis. Genuine OIDC and production-key publishing need a chosen
tag, owner secrets and deployment approval; fixture tests do not count as those.

Rollback uses a reviewed PR. Keep signing disabled rather than restoring the old
unsigned/single-APK filename assumption; never relax the fingerprint or secret
checks to make a release succeed.
